# Swarm noise budget

## Why this exists

An ERRC review on 2026-08-29, done just before merging 28 automation-generated
branches into `main`, found that most of those branches' commit volume (500-1900
commits each) was near-content-free template commits generated by scheduled
swarm/DfCM cells — not the unique work the branches existed to carry. Merging
the branches was still correct (the unique 5-10% needed to land), but leaving
the noise-generation pattern unexamined means the next 28 branches look the
same.

`scripts/branch-commit-ratio.py` is the mechanical version of that manual
classification: given a commit range, it labels each commit subject against
known noise templates and reports the substantive fraction.

```
$ python3 scripts/branch-commit-ratio.py --base origin/main --ref HEAD
BRANCH_NOISE_RATIO base=origin/main ref=HEAD
  total=2659 substantive=1479 noise=1180 ratio=55.62%
  noise breakdown:
    project-memory-receipt: 785
    control-loop-poll: 283
    falsify-probe: 49
    single-assertion-test: 47
    project-memory-template-op: 16
  verdict=ALIVE (min_ratio=15%)
```

## What counts as noise (today)

Five patterns, all traceable to specific automation surfaces in this repo:

| Label | Pattern | Source |
|---|---|---|
| `project-memory-receipt` | `receipt: Project v2 memory proxy` | `.github/workflows/project-memory-proxy.yml`'s per-run commit (see the fix below) |
| `control-loop-poll` | `control(select\|measure\|fanout\|cellN): ...` | swarm cells reading/snapshotting shared state |
| `project-memory-template-op` | `project-memory: {read\|update\|snapshot\|start\|repair\|reconcile} R<N> ...` | swarm memory round-trips |
| `single-assertion-test` | `test(ggen\|runtime): {require\|verify} ...` | one-assertion-per-commit automated test authoring |
| `falsify-probe` | `test(starter): falsify ...` | starter-journey-court probe commits |

This list is expected to grow. When a new automation cell adopts a new
low-information subject template, add a pattern to
`scripts/branch-commit-ratio.py`'s `NOISE_PATTERNS` — don't lower `--min-ratio`
to compensate; that hides the signal the ratio exists to protect.

## Where it runs

`.github/workflows/repo-hygiene.yml`'s `branch-noise-budget` job runs the script
on every pull request against its base branch and prints the ratio. **It is
report-only today** (`--enforce` is not passed): this repo's existing
automation already produces high commit volume by design (that is what a
push-triggered, receipt-per-run proxy or a scheduled polling cell does), and a
brand-new policy should not silently start failing PRs opened by that same
automation before the ratio has been observed across a representative set of
real branches.

## Rollout to a real gate

1. Let the report-only job run for a few weeks across the branches this repo's
   automation actually produces.
2. Tune `--min-ratio` (default 0.15) against the observed distribution — the
   goal is to catch branches that are *nothing but* template noise, not to
   penalize legitimate high-frequency automation that also carries real work
   (the one measured above, at 55.6%, comfortably clears any reasonable floor).
3. Flip `.github/workflows/repo-hygiene.yml`'s `branch-noise-budget` step to
   pass `--enforce`, and change its `run:` step to fail the job (remove the
   comment noting it's informational).

## Reducing the noise at the source, not just measuring it

The ratio is a smoke detector, not a fix. Two of the five patterns above have
direct source-level mitigations landed alongside this script:

- `project-memory-receipt`: the commit message itself used to be
  content-free (`receipt: Project v2 memory proxy`, identical on every run).
  It's now data-bearing (batch size + request basenames) — see
  `project-memory/README.md`'s "Commit hygiene" section and
  `scripts/compact_project_memory_receipts.py` for retroactively compacting a
  run of the old-style commits.
- `control-loop-poll` / `project-memory-template-op`: these are read-only
  state polls, not work product. The long-term fix is routing them through
  `control-plane`'s existing OCEL ingest endpoint
  (`/api/v1/ocel/batches`) instead of a git commit per poll — out of scope for
  this pass, tracked here so it isn't lost.
